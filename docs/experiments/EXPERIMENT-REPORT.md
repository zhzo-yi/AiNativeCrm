# 实验对比报告：多 Agent（A）vs Fold + Skill（B）

> 契约：`CONTRACT.md` v1.1.0　｜　数据：2026-11-10 三轮实测
> 结论：**保留 A（原多 Agent 架构）**；B 的 skill 能力转为 A 的**可选增强**。

---

## 一、实验设置

| 项 | 内容 |
|---|---|
| A 组 | `collaboration = auto`：多 Agent 编排，主循环**不加载 skill** |
| B 组 | `collaboration = skill`：主循环加载 skill（索引 + 命中正文） |
| 共同点 | **同一个协作路由器**（结构门禁 + 语义分类 + 动态 plan），委派策略完全一致 |
| 唯一变量 | 主循环是否加载 skill ✅ |
| 任务集 | T01 / T02 / T03 / T07 / T08 / T09（只读 + 调查类，写操作任务因产品证据门槛两组均拒绝，已剔除） |
| 重复 | 每任务每组 3 次（round 8/9/10），共 **36 次运行** |
| 模型 | `deepseek/deepseek-chat`（思考模式默认） |
| 数据重置 | 每次运行前恢复数据库快照（行数自检通过） |

> ⚠️ 本轮数据是在**性能事故修复之后**采集的（见 `PERF-INVESTIGATION.md`）。
> 修复前的所有 A/B 数据因延迟被放大 12 倍，已作废。

### 2.3 委派行为验证

T07 / T08（调查类任务）两组均稳定派出 **3 个子 Agent**，其余任务均不派。

→ **统一路由器生效**：A 与 B 的委派决策一致，A/B 之间不再存在"判定规则差异"这个混淆变量。

## 三、判定（依契约 §5）

| 规则 | 结果 |
|---|---|
| ① 红线否决（policy 维度失败） | 两组均无 → 通过 |
| ② 质量差 ≥ 3pp 取高分者 | 差 **0pp** → 不适用 |
| ③ ≤3pp 转看成本，降幅 ≥25% 者胜 | B 延迟慢 **7.5%**（<25%），token 多 11% → 不适用 |
| ④ 两者都不显著 → **需裁决** | ✅ 落入此条 |

**裁决**：架构无显著差异。按契约 "无差异时选择更简单方案" 的原则：

> **保留 A（原多 Agent 架构）。**

理由：
1. 质量完全等价（100% / pass^3 全过）
2. 延迟统计上不可区分（p95 98s vs 97s）
3. **A 是现有代码，B 是额外的一层**（skill 加载 + skill 库 + 播种脚本）——同效情况下应减少组件与故障面
4. B 的数据没有显示出任何可归因于 skill 的优势

## 四、B 的 skill 能力处置：转为 A 的可选增强

B 组虽然整体不占优，但它的 skill 能力**并未被证伪**——本轮实验没有充分触发 skill 的价值，原因：

- 6 个任务里只有 T03（停滞商机）会命中 `opportunity_diagnosis`，其余多数零命中
- 命中后主循环更快，但首次调用还要多付一次 skill 索引的 token

因此按决定，把 skill 作为 **A 的可选增强**（记为模式 `auto_skill`）：

| 项 | 设计 |
|---|---|
| 委派 | 与 A 完全相同（统一路由器） |
| skill | 主循环注入索引，命中时注入正文 |
| 开关 | 组织级默认关闭，可按 run 打开 |
| 预期收益 | 减少主循环的重复取证（T08 曾观察到 A 7 次工具 vs B 15 次，修复后差距消失，需重新验证） |
| 验证方式 | 与 A 同任务集对比，重点看工具调用数与 token 量 |
