## 1. 目标（终态）

在**同一个代码仓库**中，产出一套可运行的 CRM Agent 系统，能以两种运行模式完成**同一批任务**：

| 组 | 名称 | 定义 |
|---|---|---|
| **A 组** | 多 Agent 版本 | 保留现有子 Agent 编排：`OPPORTUNITY_REVIEW_PLAN` 三个只读 specialist + 父 Run 汇总（`collaboration = auto`） |
| **B 组** | Fold + 保留并行 | specialist 专长抽取为 **skill**，主循环内联执行；**跨对象盘点任务仍并行派生子 Agent**（`collaboration = skill`） |
| **C 组** | 完全 Fold（B 的对照） | 同样加载 skill，但**任何情况都不派生子 Agent**（`collaboration = skill_only`） |

**B vs C 的作用**：单独回答"保留并行子 Agent 到底值不值"——当任务需要并行时，
完全 fold 的 C 组是否比 B 组更差。这不是为了选出最终架构，而是为了**证明 B 组保留并行的
那部分不是冗余复杂度**。

**终态判定**：用同一批任务、同一套机检判据跑完两组，产出一份可复核的对比报告，并依据 §5 的决策规则**只保留其中一种模式**作为默认。

**不属于本契约范围**：群聊任务准入（admission）升级——见 §8 排除项。

## 3. 不可变项（Invariants）

以下各条在整个实验期间**不得为了让结果好看而调整**。违反任一条，实验结论作废。

| ID | 不变量 | 理由 |
|---|---|---|
| I1 | A、B 两组收到**完全相同的任务序列**，由测试脚本直接投喂，不经过群聊/渠道 | 排除入口差异混淆 |
| I2 | 每次 trial 前从**同一份种子快照**恢复数据库，并校验 188 表 / 436 函数 / 550 条 RLS 策略 | 上轮写入污染下轮 |
| I3 | 被测 Agent **不得访问**任务断言的 `expected_*` / `forbidden_*` 内容 | 防止针对性作弊 |
| I4 | 语义评审模型 **≠** 被测 Agent 所用模型 | 防自偏好抬高本组 |
| I5 | 评测任务**不得复用** `lib/ai/agents/builtins.ts` 中已存在的 12 个场景 | 训练集=测试集，防泄漏 |
| I6 | 任务 YAML 在正式跑批开始后**冻结**；中途改题则该批数据作废 | 保证可比性 |
| I7 | 两组使用**相同模型与相同 temperature**；预算上限对齐，实际用量须披露 | 成本差异须来自架构而非配额 |
| I8 | 失败/超时 run 只有在**基础设施故障**（DB 断连、模型 429/超时、进程崩溃）时可剔除，且必须逐条记录 | 剔除规则可造出任何结论 |
| I9 | 跨组比较只使用**共同指标**（strict success / cost / latency / 工具准确率）；不使用加权总分 | B 组 `collaboration_quality` 恒为 `not_run` 会改变加权分母 |

**I9 的代码依据**：`lib/ai/evals/evaluate-run.ts:473` 按"已评维度"权重归一化；`evaluate-collaboration` 在无协作时返回 `not_run` 并从分母剔除，两组总分不可比。

## 4. 指标定义

| 指标 | 定义 | 来源 |
|---|---|---|
| **strict success**（主） | 该任务声明的**全部**断言同时通过：`expected_actions` ∧ `expected_args` ∧ `expected_order` ∧ `expected_state` ∧ `forbidden_state` ∧ `forbidden_actions` ∧ `expected_response_semantic` | CRM-Agent-Bench 契约 |
| **pass^k** | 同一任务连续 k 次 trial 全部成功的比例；报告 k=1..4 | τ-bench 范式 |
| 成本 | 每任务 token 总量 + `cost_cents` + 模型调用次数 + 工具调用次数 | run events |
| 延迟 | p50 / p95 墙钟时间 | run events |
| 工具准确率 | `expected_actions` 命中率、越权工具调用次数 | run events |
| 护栏分 | 现有七维中的 `policy_compliance`（任一 fail ⇒ 该组否决） | `lib/ai/evals/profiles.ts` |
| 文本质量交叉校验 | 用户 30 对盲评（人工，不知分组） | D4 配套 |

## 5. 决策规则（预登记，不得事后修改）

1. **红线否决**：任一组出现 `policy_compliance` 失败 ⇒ 该组直接出局，不看其他指标。
2. **主判定**：比较两组 strict success。
   - 差 ≥ +3pp 且方向明确 ⇒ 采用分数更高的一组。
   - 差在 ±3pp 内 ⇒ 视为**不可区分**（D4），转为比较成本：token 或 `cost_cents` 降幅 ≥25% 的一组胜出。
   - ±3pp 内且成本差异 <25% ⇒ 判定为"架构无显著差异"，**由用户裁决**，裁决理由必须写入报告。
3. **报告义务**：无论结果，必须同时披露两组成本、延迟与实际用量差异，不得只报胜方数字。
4. **B vs C（并行是否值得保留）**：在需要并行的任务上单独比较。
   - C 组显著更差（strict success 低 ≥3pp 或 p95 延迟高 ≥30%）⇒ **B 组保留并行是正确的**，最终架构取 B。
   - B、C 无显著差异 ⇒ 并行为冗余，最终架构应取 **C**（更少组件、更少故障面）。
   - 此结论独立于 A vs fold 的主判定，但两者共同决定最终保留哪一组。
