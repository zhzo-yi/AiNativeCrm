# 性能事故复盘：每生成一个 token 就查一次数据库

> 本文记录一次真实性能排查的完整链路：从"任务要跑 20 分钟"到定位根因、修复、验证。
> 所有数据来自 `llm_calls` / `ai_agent_run_events` 实测，不是估算。

- 发现时间：2026-11-10
- 影响范围：所有走工作台（workbench）的 Agent 任务
- 严重程度：阻断级（单任务 4–20 分钟，无法上线）
- 修复后：同任务 53–98 秒

---

## 一、现象

| 任务 | 修复前耗时 |
|---|---|
| T01 客户 360 摘要（单对象只读） | 225–321 秒 |
| T03 停滞商机（单对象只读） | 296–389 秒 |
| T07 商机复盘（跨域 + 3 子 Agent） | **1074–1214 秒（多次撞 20 分钟上限）** |

用户的判断是"真上线绝对不允许这么长时间无响应"。

## 二、排查过程（六步，每步都用数据排除一个假设）

### 第 1 步：先加遥测，不猜

系统里本来就有 `llm_calls` 表，记录每次模型调用的 token、延迟、缓存命中、成本。但跑批在每次试验前会重置数据库，把这些记录抹掉了。

**动作**：在跑批的 `collectEvidence` 里补一条查询，按 `workbench_run_id` 把 `llm_calls` 快照进结果文件。

**拿到基线**：

```
purpose             n   平均延迟     输入 token   输出 token
agent_turn          6   433,772 ms    31,867       10,022
agent_specialist    3    12,949 ms     5,976        2,688
collaboration_router 2    2,890 ms       830          387
```

**关键观察**：主循环调用（`agent_turn`）平均 434 秒，而子 Agent（`agent_specialist`）只要 13 秒——**33 倍差距**。

### 第 2 步：排除"上下文太长"

单条记录显示：输入 3,032 token、输出 1,912 token，却花了 321 秒。

这个输入输出量级很正常（不算长上下文），却产生了 321 秒。**上下文长度不足以解释。**

### 第 3 步：排除"模型/网络慢"——直连对照实验

写了一个探针脚本绕过应用，直接调 DeepSeek API：

```
非流式 第 1 次: 4.5s  (prompt 1114 tok / completion 229 tok)
非流式 第 2 次: 6.3s  (prompt 1114 tok / completion 493 tok)
流式   第 1 次: 5.1s  首字节 0.5s (completion 423 tok)
流式   第 2 次: 3.5s  首字节 0.7s (completion 263 tok)

直连平均: 4.8 秒
应用内:   321.7 秒   ← 差 67 倍
```

**结论：DeepSeek 本身只要 5 秒，问题在应用层。**

### 第 4 步：排除"工具定义拖慢"

又做了对照：直连时带上 5 个工具定义、以及超长 system prompt：

```
无工具      : 38.9 tok/s
带 5 个工具 : 69.9 tok/s
带工具+长文 : 109.9 tok/s
```

**结论：工具和长上下文都不影响生成速度，甚至更快。**

### 第 5 步：排除"思考模式"

临时关闭思考模式（`DEEPSEEK_THINKING=disabled`）重跑同一任务：

```
思考开: 321.7s
思考关: 224.7s   ← 快了 30%，但吞吐仍是 6 tok/s
```

**结论：思考模式只影响输出量，不是吞吐瓶颈。**

### 第 6 步：抓住恒定吞吐率

把所有慢调用放在一起算：

| 运行 | 输出 token | 延迟 | 每 token |
|---|---|---|---|
| T01 | 1,912 | 321.7s | 168 ms |
| T01（思考关） | 1,459 | 224.7s | 154 ms |
| （另一批） | 3,177 | 529.0s | 166 ms |
| （另一批） | 2,208 | 368.5s | 167 ms |

**四个样本，吞吐恒定在 6 tok/s（每 token 150–170ms）。**

这个数值极其可疑——**150ms 不是模型生成一个 token 的时间，而是一次远程数据库往返的时间。**（Supabase 同区域查询延迟实测约 150ms）

于是假设变成：**每生成一个 token 就有一次数据库调用。**

## 三、根因

顺着"事件流"追，找到了完整链条：

```
① pi-agent-core/agent-loop.js:246
   流式响应每来一个 text_delta（每个 token）
   → await emit({ type: "message_update" })

② pi/runtime.ts:536
   agent.subscribe(async (event) => { ... await input.onEvent?.(mapped) })

③ workbench-start-job.ts onEvent（修复前）
   onEvent: async (event) => {
     await beforeSideEffect();        ← 无条件执行，对所有事件
     if (event.type === "tool_execution_start") { ... }
     else if (event.type === "tool_execution_end") { ... }
     else if (event.type === "turn_end") { ... }
   }

④ beforeSideEffect = () => assertWorkbenchJobLease(pool, job, workerId)
   → 一次数据库查询
```

**`message_update` 在 ① 中每 token 触发一次，但它既不匹配 ③ 里任何分支，也没有被提前 return——只有开头那行 `await beforeSideEffect()` 被执行了。**

于是：**生成 1,459 个 token = 1,459 次数据库往返 × 154ms = 224.7 秒。**

与实测值**完全吻合**。

## 四、为什么这个 bug 很难发现

| 原因 | 说明 |
|---|---|
| 单行代码看起来完全正确 | "写库前校验租约"本身是合理的防御 |
| 逻辑没有错 | 错的不是逻辑，是**执行频率** |
| 只有两个数字相乘才暴露 | 事件频率（每 token）× 数据库延迟（150ms） |
| 本地环境测不出来 | 本地 Postgres 往返 ~1ms，2000 token 也只多 2 秒 |
| 症状像"模型慢" | 外部表现就是"AI 在思考很久" |

## 五、修复

把租约校验从"每个事件"移到"真的要写库之前"：

```ts
// 修复前
onEvent: async (event) => {
  await beforeSideEffect();          // ← 每 token 查一次库
  if (tool_execution_start) { ...写库... }
  else if (tool_execution_end) { ...写库... }
  else if (turn_end) { ...写库... }
}

// 修复后
onEvent: async (event) => {
  if (tool_execution_start) { await beforeSideEffect(); ...写库... }
  else if (tool_execution_end) { await beforeSideEffect(); ...写库... }
  else if (turn_end) { await beforeSideEffect(); ...写库... }
}
```

**语义上也更正确**：只有要产生副作用时才需要确认自己仍持有租约。`message_update` 是纯流式增量，不写库，不需要校验。

代码位置：`lib/ai/agents/workbench-start-job.ts`（约 576–613 行）

## 六、验证

### 单元级：吞吐率

| 指标 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| 生成吞吐 | 6 tok/s | **81.6–102 tok/s** | **13–17 倍** |
| 与直连 API 上限（78–110 tok/s）对比 | 差 15 倍 | **已对齐** | — |

### 任务级

| 任务 | 修复前 | 修复后 | 结果 |
|---|---|---|---|
| T01 客户 360（单对象） | 225–321s | **53s** | strict 通过 |
| T07 商机复盘（3 子 Agent） | 1074–1214s（超时） | **98s** | strict 通过 |

T07 明细：
```
collaboration_router: 2.1s (93 tok/s)   → 决策 delegate，派出 3 个子 Agent
agent_turn:          39.7s (102 tok/s)  输入 7,838 / 输出 4,047 token
子 run: 3 个
工具调用: 6 次（修复前 17 次）
```

### 一个附带的连锁效应

修复前超时的那几次运行里，主循环工具调用高达 **17 次**；修复后只有 **6 次**。

原因：每 token 卡 150ms 会让单轮变慢，模型在预算压力下更容易反复补查，形成"越慢越乱、越乱越慢"的正反馈。**修掉延迟也顺带修掉了这个放大效应。**

## 八、可复用的教训

1. **外部依赖的调用频率 = 性能。** 判断一条代码路径是否昂贵，不能只看它做了什么，还要看它被调用了多少次。
2. **先加遥测，再优化。** 这次能在 6 步内定位，靠的是 `llm_calls` 里现成的 token/延迟数据；没有它，所有分析都是猜。
3. **"恒定吞吐率"是强信号。** 不同任务、不同输出长度下吞吐都是 6 tok/s，说明瓶颈是固定成本，而不是任务复杂度。
4. **直连对照是最便宜的排除法。** 一个 20 行的探针脚本，5 秒内就能判定"是模型慢还是应用慢"。
5. **本地开发环境会掩盖这类问题。** 建议给关键路径加一个"远程数据库延迟"的默认假设。
